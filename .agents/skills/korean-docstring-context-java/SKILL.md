# Korean Docstring With Project Context (Java)

## 목적

프로젝트 전체와 하위 디렉토리에서 Java Javadoc을 작성할 때, Google 스타일과 Effective Java 원칙을 결합해 한국어로 작성한다. 처음 보는 사람이 호출 흐름, 사용 위치, 변수/클래스 역할까지 이해할 수 있도록 맥락 정보를 반드시 포함한다.

## 적용 범위

- Java (Spring Boot): Javadoc

## 스프링 문서화 연동 (spring-documentize 준수)

- 컨트롤러/DTO 문서화는 Swagger/OpenAPI 규칙을 함께 따른다.
- Swagger 설명문은 "한글 설명 / English description" 형식으로 작성한다.
- 복잡한 엔드포인트는 HTTP 요청/응답 예시를 JavaDoc에 포함한다.

## 핵심 원칙 (Google + Effective Java)

- API 계약을 문서화한다: 전제조건, 후속조건, 부작용, 예외 조건, 스레드 안전성.
- 요약은 한 줄, 명확한 동작/역할을 표현한다.
- 타입 시그니처에 이미 있는 정보는 반복하지 말고, 의도/규칙/범위/단위/기본값을 기록한다.
- 문서가 코드보다 오래 남는다는 전제로 유지보수 가능성을 최우선으로 한다.
- 프로젝트 맥락을 반드시 포함한다: 호출 위치, 사용 목적, 관련 클래스/모듈, 데이터 흐름.
- 이해 가능한 표현을 사용한다: 생략 대신 풀어 쓰고, 처음 보는 사람이 바로 이해할 수 있도록 설명한다.
- "아주 친절한" 톤을 유지한다: 용어 정의, 배경 설명, 맥락 연결을 충분히 포함한다.

## 아주 친절한 docstring 섹션 (강제)

모든 public/protected 대상과 핵심 로직에는 아래 섹션을 반드시 포함한다.

- 섹션 제목: `아주 친절한 설명:`
- 포함 내용:
  - 용어/약어 풀이 (예: SessionCreated = 세션 생성 이벤트)
  - 흐름 요약 (사용자 행동 → 호출 → 저장/처리 → 반환/후속 동작)
  - 초보자 관점의 주의점 (실수하기 쉬운 조건, null/빈 값 처리 등)
- 길이 기준: 2~4문장, 한 문장당 20~40자 내외의 짧고 명확한 문장

## 필수 맥락 정보 (누락 금지)

모든 public/protected 대상과 핵심 로직에는 아래 정보를 포함한다.

- 호출자/사용자: 어떤 클래스/레이어가 호출하는지
- 사용 시점/목적: 언제, 왜 사용되는지
- 역할/범위: 변수/클래스/메서드가 시스템에서 맡는 책임
- 데이터 흐름: 입력이 어디서 오고 결과가 어디로 가는지
- 부작용: DB 변경, 캐시 갱신, 외부 API 호출, 이벤트 발행
- 예외/오류: 어떤 조건에서 발생하는지
- 계약 정보: 전제조건/후속조건, 허용 범위, 기본값

## 필수 태그 규칙 (누락 금지)

- 모든 파라미터에 `@param`을 작성한다. 파라미터 개수와 태그 개수가 반드시 일치해야 한다.
- 반환값이 있는 경우 `@return`을 반드시 작성한다.
- 반환값이 없는 `void` 메서드는 `@return`을 생략하고, 본문에 "반환값 없음"을 명시한다.
- 실제로 던질 수 있는 예외는 `@throws`로 모두 기록한다. (도메인 예외/런타임 예외 포함)
- 예외는 "언제" 발생하는지 조건을 구체적으로 적는다.

## 작성 절차

1. 대상 식별: 클래스/메서드/필드/함수 중 문서화 대상 선택.
2. 기존 영어 문서 확인: 기존 영문 Javadoc이 있으면 내용을 참고한다.
3. 영문 삭제 및 한국어 전환: 영문 텍스트를 제거하고, 동일한 의미를 한국어로 다시 작성한다.
4. 호출 흐름 파악: 참조/호출 위치를 검색한다 (LSP references, Grep).
5. 맥락 메모 작성: 호출자, 관련 클래스, 데이터 흐름, 부작용, 전제/후속조건을 정리.
6. 요약 작성: 한 줄 요약 + 빈 줄.
7. 상세 작성: 호출자/사용 시점/역할/데이터 흐름/부작용/예외/스레드 안전성 순으로 기록.
8. 태그 작성: `@param`, `@return`, `@throws`를 필수 규칙에 맞춰 작성.
9. 예시 추가: 컨트롤러/DTO는 HTTP 요청/응답 또는 사용 예시를 추가한다.

## Java Javadoc (Google 스타일 + Effective Java)

### 규칙

- 요약은 명사구/동사구로 시작하고 "이 메서드는" 금지.
- 단락은 빈 줄과 `<p>`로 구분.
- 태그 순서: `@param`, `@return`, `@throws`, `@deprecated`.
- 계약/경계 조건/부작용/스레드 안전성을 명시.
- 이해 가능한 문장으로 작성한다. 축약어나 내부 용어는 괄호로 풀어 쓴다.
- "아주 친절한 설명" 섹션을 필수로 넣는다.

### 템플릿

```java
/**
 * [한 줄 요약 - 명사구/동사구]
 *
 * <p>
 * 호출자/맥락: [어떤 계층/기능에서 호출되는지, 사용 목적]
 *
 * <p>
 * 책임:
 * <ul>
 *   <li>[역할 1]</li>
 *   <li>[역할 2]</li>
 * </ul>
 *
 * <p>
 * 데이터 흐름: [입력 출처] -> [처리] -> [출력/저장 위치]
 *
 * <p>
 * 부작용: [DB/캐시/외부 호출/이벤트]
 *
 * <p>
 * 스레드 안전성: [thread-safe 여부와 조건]
 *
 * <p>
 * 예외: [예외가 발생하는 조건을 한국어로 설명]
 *
 * <p>
 * 반환값: [반환값 의미 또는 "반환값 없음"]
 *
 * <p>
 * 아주 친절한 설명: [용어 풀이] [흐름 요약] [초보자 관점 주의점]
 *
 * @param param [의도, 제약, 단위]
 * @return [반환 값 의미, null 여부]
 * @throws SomeException [발생 조건]
 */
```

### 예시

```java
/**
 * 세션 소유권을 검증한다.
 *
 * <p>
 * 호출자/맥락: 컨트롤러에서 요청한 세션 접근을 처리하기 전에 서비스 계층에서 호출된다.
 *
 * <p>
 * 책임:
 * <ul>
 *   <li>세션 작성자와 요청 사용자 일치 여부 확인</li>
 *   <li>회사 소속 일치 여부 확인</li>
 * </ul>
 *
 * <p>
 * 데이터 흐름: Session -> Membership 조회 -> 검증 결과 예외 처리
 *
 * <p>
 * 부작용: 없음 (검증 실패 시 예외 발생)
 *
 * <p>
 * 반환값: 반환값 없음
 *
 * <p>
 * 아주 친절한 설명: Session은 회의 세션 객체를 의미한다. 이 메서드는 컨트롤러 요청을 받아
```

## 금지 사항

- 호출 위치/사용 맥락을 생략하지 않는다.
- 타입 시그니처에 있는 정보만 반복하지 않는다.
- 구현 상세(조건문/루프 구조 등)만 설명하지 않는다.
- 근거 없는 추측을 쓰지 않는다. 호출자/흐름은 반드시 확인 후 기록한다.
- `@param`, `@return`, `@throws` 누락을 용납하지 않는다.
- "아주 친절한 설명" 섹션 누락을 용납하지 않는다.

## 빠른 체크리스트

- 요약 한 줄이 명확한가
- 호출자/사용 목적/데이터 흐름이 포함됐는가
- 전제조건/후속조건/부작용/예외가 포함됐는가
- `@param` 개수와 실제 파라미터 개수가 일치하는가
- 반환값이 있으면 `@return`이 있는가 (void면 본문에 "반환값 없음")
- 발생 가능한 예외가 모두 `@throws`로 기록됐는가
- "아주 친절한 설명" 섹션이 포함됐는가
- 용어 풀이/흐름 요약/주의점이 모두 들어갔는가
- 한국어로 작성했는가
- 문서가 처음 보는 사람의 이해를 돕는가
